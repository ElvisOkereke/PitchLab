### T1: "For you to check" status and list (owner decision 1)
- **New status.** Add `'needs_review'` to the `claim_verified` pg enum, with a drizzle-kit migration (`ALTER TYPE … ADD VALUE`, generated by `npx drizzle-kit generate`). Add nullable `claims.reviewNote text` in the same migration. It holds the reason the owner must check.
- **Competitor claims become two kinds** (`deep-case.ts`):
  - `section: 'competitor'`: text `"<name>"`, the product page. The check is "the page describes this product/company".
  - `section: 'competitor-pricing'`: inserted ONLY when the case quotes a concrete figure, i.e. pricing contains a digit. Text `"<name> pricing: <pricing>"`, same url.
  - When pricing has no figure ("Not published", "Contact sales"…), insert no pricing claim. The export shows the pricing cell with "🔍 not published — check" and lists it in "For you to check".
  - Both kinds count toward the existing 15-competitor cap per case, counted as competitors (not rows).
- **verify.ts statuses:**
  - Page unreachable or unreadable → `unreachable` (unchanged), with `reviewNote` "page could not be loaded by the checker — open it yourself".
  - Judge confidence in [0.3, 0.6) → `needs_review`, `reviewNote` "checker unsure (confidence X)". This applies whether `supported` is true or false.
  - `supported && confidence ≥ 0.6` → verified. `!supported && confidence ≥ 0.6` → unsupported. Confidence < 0.3 → unsupported.
  - Export `REVIEW_CONFIDENCE_FLOOR = 0.3` beside the existing `MIN_JUDGE_CONFIDENCE`.
- **verify-claim prompt:** new version `verify-claim.v2.md`. For `competitor` claims, ask whether the page is about the named product or company. For `competitor-pricing`, ask whether the page shows that pricing. Other sections are unchanged. Pass the section into the prompt.
- **score.ts:** `needs_review` counts as non-credit in the evidence ratio (like unreachable). Stats text reports needs_review counts separately.
- **export-markdown.ts:**
  - 🔍 emoji for `needs_review`.
  - New section **"For you to check"**, placed right after the Summary (before Evidence). It lists every claim with status `unreachable` or `needs_review`, plus every competitor with unpublished pricing. Each line gives the item, its link, and the reason (`reviewNote` or a fixed reason). If there are none, write "Nothing — every displayed source was confirmed or flagged."
  - Real `unsupported` items stay ❌ and are NOT in this list.
  - The Competitors table gets two status columns: Product and Pricing.
- **Tests:**
  - Migration applies (testDb).
  - Competitor with "Not published" → product claim only.
  - Competitor with "$49/mo" → product + pricing claims.
  - Judge 0.45 → needs_review with note.
  - Unreachable gets a note.
  - Score ratio treats needs_review as non-credit.
  - The export "For you to check" section lists an unreachable link, a needs_review claim and an unpublished price, and does not list an unsupported claim.
  - Empty case → the "Nothing — …" line.

### T2: Verify GitHub signals via the GitHub API (decision 2)
- In `verify.ts`, for claims whose `sourceUrl` matches `https://github.com/<owner>/<repo>/issues/<n>` (or `/pull/<n>`), fetch the text from `https://api.github.com/repos/<owner>/<repo>/issues/<n>` plus `/comments?per_page=100`. Concatenate title + body + comment bodies. Use the Bearer `GITHUB_TOKEN` if set in env (add it to `StageDeps` or a verify option; don't read `process.env` inside the stage). Then run the same matching and judge flow on that text.
- Use the existing guarded `fetchPage` if it can return JSON text. Otherwise use a small GET-only JSON helper with the 15s timeout and 2MB cap (reuse `readCapped`), hard-wired to host `api.github.com`.
- API failure (non-2xx, rate limit) → fall back to the normal page fetch path.
- Cache per URL, as today.
- Tests (injected fetch, no network): a GitHub issue URL whose API body contains the quote → verified via the fast path; API 403 → falls back to the page path; a non-GitHub URL is unaffected.

### T3: Diverse gate entrants (decision 3)
- **ideate:**
  - New prompt `ideate.v5.md`, copied from v4. Each idea must declare `mechanism` from a fixed enum: `monitoring`, `money_recovery`, `workflow_automation`, `data_product`, `integration`, `compliance`, `marketplace`, `other`. It also declares `buyerType`: a short noun phrase, e.g. "web agency", "multi-location service business", "property manager".
  - The ideate schema gains both fields: a zod enum and a string.
  - Add nullable columns `ideas.mechanism text` and `ideas.buyerType text` (migration). Store them on insert.
  - Owner ideas: the owner-idea extraction schema also returns both fields (prompt `owner-idea.v3.md`).
- **screen.ts:** when picking generated winners, in rank order, skip a candidate (→ `screened_out`) if any of these hold:
  - (a) 2 already-advanced generated ideas share its `mechanism`. Null mechanism is never capped.
  - (b) existing near-twin rule (cosine > 0.8 to an advanced idea).
  - (c) cosine ≥ 0.82 to ANY idea from ANY run that has a case (`cases.ideaId`). That catches regenerated copies of ideas already written up. Do this via SQL `1 - cosineDistance` against ideas joined to cases, ignoring NaN (as in dedupe).
  - Keep filling `advanceCount` from the remaining ranked list.
  - Log each skip reason via `deps.log`.
- **Tests:**
  - 4 high-scoring `monitoring` ideas + 1 `money_recovery`, `advanceCount` 3 → 2 monitoring + 1 money_recovery advanced.
  - A candidate similar (≥ 0.82) to a past idea with a case → skipped.
  - Null mechanism → not capped.
  - Owner ideas unaffected.

### T4: Cited signals only + entity decoding (decision 4)
- **Writer reports its signals:**
  - `CaseDraftSchema` gains `usedSignalUrls: string[]`, the URLs of provided signals the writer actually relied on.
  - Prompt `case-write.v3.md`, copied from v2, instructs the writer to fill it from `<signals>` only.
- **deep-case.ts stored signals** = real signal rows whose url ∈ `usedSignalUrls` (validated against the provided rows; unknown urls ignored), then banned-filtered and capped at 15 as today. If the writer returns none, store none and add nothing. Signal claim rows follow the stored list.
- **Entity decoding:**
  - `cleanText` in `sources/types.ts` decodes ALL numeric entities (`&#\d+;`, `&#x[0-9a-f]+;`), guarding against invalid code points, plus named `&rsquo; &lsquo; &ldquo; &rdquo; &hellip; &mdash; &ndash; &nbsp; &amp; &lt; &gt; &quot; &apos;`. Then it strips tags as today, so decoded `<` and `>` are still neutralised by the existing steps.
  - Apply the same decode helper to `RawItem.text`/`title` from research sources in harvest.
  - In export, decode legacy stored quotes before escaping. Decode first, then escape (R13).
- **Tests:**
  - `&#8217;`, `&#x2019;` and `&rsquo;` all decode to ’.
  - An invalid code point stays literal.
  - Deep-case stores only used signals.
  - The export renders a legacy quote containing `&#8217;` as ’.
